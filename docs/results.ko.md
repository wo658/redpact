# 실행 근거 읽기

`get_review_context`가 반환한 정확한 `reviewPath`를 같은 뷰어 인스턴스에서 여세요.
URL에는 실행 종류와 식별이 담깁니다. 뷰어는 기록의 워크트리를 해석하며 다른 곳에서
체크아웃을 선택해도 그 대상을 바꾸지 않습니다. 실행 링크가 없으면 채팅에서 기록을
열도록 안내합니다.

## 요청, 실행과 이력

대기 중인 요청은 실행이 아닙니다. Ask에서는 명시적 승인 버튼을 누르기 전에 캡처된
명령이나 대상, 설정·입력 식별, Integration 서비스·의존성·테스트 소스를 확인하세요.
Integration은 환경 승인 다음에 테스트 승인을 요구합니다. 취소는 승인이나 수락이
아닙니다. 규약을 지키는 MCP App도 채팅 안에서 같은 사람의 결정을 제공합니다.
[인터페이스](interfaces.md)를 참고하세요.

실행 검토에는 기록된 결과, 제한된 진단, 소스와 사용 가능한 브라우저 산출물이
나옵니다. 이력은 기록의 워크트리에 한정되며 다른 정확한 기록을 엽니다. 현재
체크아웃이 없어도 보존된 결과는 유효합니다. 워크트리가 없는 기록은 무관한
체크아웃의 이력을 대신 사용하지 않습니다.

| 근거 | 증명하는 범위 |
| --- | --- |
| Unit | 설정된 전체 명령, 종료 상태, 출력과 정리 사실 |
| Integration | 제출된 테스트·도우미 소스, 관찰된 사례·단계와 환경 사실 |
| Playwright functional | 실제 브라우저 단언과 사용 가능한 산출물 |
| Playwright capture | 사람이 시각적으로 판단할 기록된 화면 |

단언과 기록된 소스를 함께 읽으세요. 제목만으로 검증 내용을 알 수 없습니다.
캡처 성공은 시각적 수락이 아니며 종료 코드로 Unit 사례별 결과를 만들어내지 않습니다.
소스 조회는 수정된 작업 파일이 아닌 보존된 입력을 사용합니다.

## 결과, 최신성과 수락

통과한 실행은 캡처된 입력을 설명합니다. 이후 수정에는 새 검증이 필요합니다.
`get_review_context`는 실행 결과, 소스 최신성과 사람의 수락을 분리합니다.
검증하지 않은 최신성은 `unknown`, 수락은 `not_recorded`로 남습니다.
재시도를 논의할 때 최신 파일이나 이전 통과를 현재 근거로 간주하지 말고 실행 ID를 비교하세요.

준비·수집·단언·정리 실패는 해결 방법이 다릅니다. 기록은 관련 첫 오류와 남은 자원의
참조를 보존합니다. Playwright가 끝났다는 사실만으로 자원 삭제를 증명하지 못합니다.
명시적 정리 근거가 없으면 요약은 `unknown`입니다. 정리 오류는 테스트 판정과 별개로
실패를 표시합니다. 지원하는 취소·정리 재시도 후 상태를 다시 확인하세요.

## 채팅에서 계속하기

결과·제한된 로그·기록된 테스트 소스·PNG는 `get_execution`, 체크아웃의 보존된 이력은
`list_executions`로 읽습니다. 기록 전체를 복사하지 않고 실패를 설명하려면
`get_review_context`를 사용하세요. 공유 전에 비공개 데이터를 검토하세요. 로그 마스킹은
스크린샷이나 캡처된 파일을 정제하지 않습니다.

수정을 요청할 때 원래 실패한 시도를 남기고 입력 변경 후 새 요청을 제출하세요.
실행 승인은 커밋·병합·게시나 코드 수락을 허가하지 않습니다.
[문제 해결](troubleshooting.md)과 [테스트 작성](tests.md)에 진단과 검증 범위를 설명합니다.
