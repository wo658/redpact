# 첫 프로젝트 설정

먼저 [Redpact 인스턴스와 MCP 연결](installation.md)을 준비하세요. 테스트할 애플리케이션의 실제 체크아웃을 선택합니다. Redpact는 Git 저장소와 디렉터리 프로젝트를 지원합니다. 워크트리는 애플리케이션과 테스트 파일을 실행할 구체적인 체크아웃을 가리킵니다.

## 디렉터리 연결

뷰어의 프로젝트 연결 양식에 애플리케이션의 절대 경로를 입력하거나, 서버를 시작할 때 `--project /absolute/path/to/your-project`를 지정하세요. 연결된 Git 프로젝트는 기존 워크트리를 자동으로 찾습니다. 탐색만으로 브랜치를 생성하거나 테스트를 실행하지는 않습니다.

에이전트는 MCP에서 체크아웃의 절대 경로를 직접 지정할 수 있습니다. `run_tests` 전에 별도의 MCP 등록이나 제출 작업을 할 필요는 없습니다.

## 에이전트에게 애플리케이션 조사 요청

다음처럼 요청하세요.

> 이 프로젝트에 Redpact 관리형 통합 테스트를 설정해줘. 이 체크아웃에 configure describe를 호출하고 실제 빌드·시작 명령, 의존성, Docker 파일을 확인한 뒤 프로젝트 설정을 작성해줘. 기존 설정은 보존해줘. 사용할 서비스와 의존성 선택을 검증하고, 실행 시 추가로 확인해야 할 사항을 알려줘. 아직 테스트는 시작하지 마.

에이전트는 애플리케이션을 실행하는 Compose 서비스, 사용하는 의존성, 테스트에 필요한 연결 값을 파악해야 합니다. Docker 또는 Compose 파일이 없다면 실제 애플리케이션 동작을 바탕으로 작성해야 합니다. mock 모드를 선언하는 것만으로 mock 구현이 생기지는 않습니다.

단위 테스트만 설정하려면 단위 테스트용 Dockerfile과 명령을 요청하세요. MCP `run_tests`는 관리형 Vitest 통합 테스트를 실행합니다. 단위 테스트 명령과 Playwright 대상은 별도의 실행 제어를 사용합니다. [테스트 종류와 작성 방법](tests.md)을 참고하세요.

## 정의와 실행 선택 구분

기본 체크아웃에 공통 `.redpact/settings.json` 하나를 두고 연결된 워크트리에서 공유합니다. 설정을 작성할 디렉터리는 `configure`가 반환한 `rulesRoot`로 확인하세요. 애플리케이션, Compose, 테스트 경로는 선택한 체크아웃을 기준으로 해석합니다.

설정 파일에는 Compose 파일, 의존성, 환경변수 바인딩, 테스트 위치를 정의합니다. 실행 선택은 해당 실행에서 사용할 루트 서비스와 의존성 모드를 지정합니다. 모드 이름은 `isolated`, `shared-local`, `remote`, `mock`이며 프로젝트에 실제로 구현된 모드만 설정하세요.

`app` Compose 서비스와 결제 mock 구현이 있는 프로젝트라면 다음처럼 선택할 수 있습니다.

```json
{
  "services": ["app"],
  "select": { "payments": "mock" }
}
```

실제 프로젝트에 존재하는 이름을 사용하세요. 의존성 추천이 표시된다고 해당 의존성이 선택되거나 실행 준비가 확인되는 것은 아닙니다.

체크아웃은 `.redpact/selection.json` 또는 Environment 화면을 통해 선택을 저장할 수 있습니다. 실행 시 명시적으로 전달한 선택이 저장된 값보다 우선합니다. 선택을 저장해도 컨테이너는 준비되지 않습니다. 공통 정의는 체크아웃별 덮어쓰기 없이 `.redpact/settings.json`에 유지합니다.

## 실행 전 검증

에이전트에게 사용할 체크아웃과 선택으로 `configure`를 호출하도록 요청하세요.

```json
{
  "action": "validate",
  "path": "/absolute/path/to/your-project",
  "selection": {
    "services": ["app"],
    "select": { "payments": "mock" }
  }
}
```

필드와 원본 위치에 대한 진단을 확인해 수정한 뒤 다시 검증하세요. 검증은 작성된 설정과 선택을 확인합니다. Docker에 연결하거나, 애플리케이션 상태를 확인하거나, 시크릿 값을 해석하거나, 테스트를 실행하거나, 사람의 승인을 확정하지 않습니다.

프로젝트 연결 시 설정 파일이 없으면 빈 설정을 만들 수 있습니다. 빈 설정으로 프로젝트를 살펴볼 수는 있지만 실행 가능한 애플리케이션 환경을 제공하지는 않습니다. 기존의 잘못된 파일은 수정할 수 있도록 그대로 남겨둡니다.

민감한 값은 시크릿 참조로 선언하고 지원되는 사용자 인터페이스에서 직접 입력하세요. 자격 증명 값을 에이전트 프롬프트나 설정 파일에 넣지 마세요. 기본값, 덮어쓰기, 제거, 시크릿은 [설정 레퍼런스](configuration.md)를 참고하세요.

## 애플리케이션 구성부터 정리하기

설정을 작성하기 전에 저장소에서 확인한 내용을 짧게 정리하세요. 에이전트가 각 서비스와 환경 변수 연결이 왜 필요한지 설명하는 데 도움이 됩니다.

| 살펴볼 곳 | 기록할 내용 | 사용하는 곳 |
|---|---|---|
| 패키지 스크립트와 Dockerfile | 빌드 명령, 종료 가능한 테스트 명령, 런타임 작업 디렉터리 | Unit 설정과 애플리케이션 이미지 |
| 애플리케이션 시작 코드 | Compose 서비스명, 수신 인터페이스, 내부 포트, health 경로 | 관리형 애플리케이션 준비와 테스트 연결 |
| 의존성 호출부 | 실제 연동과 구현된 로컬 대체 동작 | 실행 가능한 의존성 모드 |
| 기존 테스트 파일 | 테스트 루트, 헬퍼 import, 필요한 환경 변수 | 소스 수집과 `tests.env` |
| 브라우저 경로 | 접근 가능한 경로와 확인 가능한 준비 상태 | Playwright 시나리오와 캡처 |

예를 들어 “애플리케이션이 `PAYMENTS_MODE=mock`을 읽고 해당 분기를 구현한다”는 mock 선언의 근거입니다. “결제 mock이 있으면 좋겠다”는 앞으로 필요한 개발을 뜻합니다. 설정 보고서에서도 둘을 구분하세요.

## 예시: 기본 체크아웃과 기능 워크트리

기본 체크아웃이 `/work/shop`, 기능 체크아웃이 `/work/shop-checkout`이라고 가정해 보겠습니다. 기능을 검토할 때는 `configure`와 `run_tests`에 기능 체크아웃 경로를 사용합니다.

| 입력 | 예시에서의 위치 |
|---|---|
| 공통 Redpact 정의 | `/work/shop/.redpact/settings.json` |
| 기능 체크아웃의 실행 선택 | `/work/shop-checkout/.redpact/selection.json` |
| `compose.yaml`로 선언한 Compose 파일 | `/work/shop-checkout/compose.yaml` |
| `tests/http.test.ts`로 선언한 통합 테스트 소스 | `/work/shop-checkout/tests/http.test.ts` |

폴더 이름으로 기본 체크아웃을 추측하지 말고 반환된 `rulesRoot`를 사용하세요. 공통 설정이 유효해도 기능 워크트리에 참조한 Compose 서비스나 테스트 소스가 없으면 실행할 수 없습니다. 해당 입력을 수정한 뒤에는 기능 경로를 대상으로 검증하세요.

## 설정 보고서에서 확인할 내용

유용한 보고서에는 공통 설정 파일, 실행 체크아웃, 사용 가능한 테스트 종류, 선택한 서비스와 의존성 모드, 부족한 준비 사항이 들어갑니다. 처음 실행할 시나리오와 그 시나리오로 확인할 내용도 명시해야 합니다.

예를 들어 “결제 mock이 구현돼 있고 선택됐으며 설정 검증을 통과했습니다. 첫 통합 시나리오는 `APP_URL`로 결제 응답을 확인합니다. Docker 준비와 해당 단언은 아직 실행하지 않았습니다”라고 정리할 수 있습니다. 그러면 설정을 테스트 성공으로 오해하지 않고 다음 행동을 결정할 수 있습니다.

## 설정 마무리

첫 실행 전 체크아웃을 확인하고 명시적인 선택으로 공통 설정을 검증한 뒤, 설정된 디렉터리에 테스트 소스를 두세요. Docker 실행 준비와 애플리케이션 상태는 실제 실행에서 관찰하기 전까지 확인되지 않은 상태입니다.

[첫 관리형 테스트 실행](first-run.md)으로 이어가세요.
