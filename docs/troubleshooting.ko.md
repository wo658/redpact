# 문제 해결

실제 인스턴스·체크아웃·반환된 식별부터 확인합니다. `get_review_context`를 읽고
`get_execution`으로 기록된 결과·로그·소스를 확인하세요. 정확한 검토 경로를 여세요.
기존 요청의 진행을 읽기 위해 새 요청을 만들지 않습니다.

| 관찰 | 확인할 내용 |
| --- | --- |
| MCP 연결 불가 | 런타임 health, 실제 MCP origin, 호스트 도구 목록 갱신 |
| 설정 진단 | 파일·필드, 공유 기본 루트와 선택한 체크아웃 |
| 승인 대기 | 캡처된 요청과 사람의 명시적 App·뷰어 제어 |
| 단언 미도달 | 소스 수집·import·이미지 빌드·준비 상태 |
| 단언 실패 | 기대·실제 값, fixture 데이터와 애플리케이션 동작 |
| 테스트 종료 후 자원 잔류 | 별도 정리 오류와 남은 자원 식별 |
| 화면 누락 | 정확한 실행·대상과 시나리오의 해당 PNG 첨부 여부 |

## 연결과 식별

에이전트와 뷰어는 같은 인스턴스를 사용해야 합니다. 일반 데스크톱·플러그인 기본값은
54321, 로컬 App Page는 54322, 소스 CLI는 54318입니다. 데이터 디렉터리는 별개입니다.
플러그인 설치만으로 모든 런타임을 시작하거나 캐시된 MCP 도구 목록을 새로고치지
않습니다. [설치](installation.md)를 참고하세요. 잘못된 주소를 해결하려고
Host·Origin·Fetch Metadata 검사를 끄지 마세요.

인스턴스 `projects`, 관찰된 체크아웃 연결과 `configure` 진단을 확인합니다. 공유
`rulesRoot`가 설정을, 실행 `projectRoot`가 소스를 제공합니다. 연결된 워크트리의
설정 복사본은 기본 설정을 덮어쓰지 않습니다. 사라진 체크아웃은 이력을 남기지만
실행할 수 없습니다. 호스트 에이전트가 Git·워크트리 경로를 복구하며 뷰어에는 프로젝트
관리나 폴더 선택기가 없습니다.

## 대기 중이거나 오래된 승인

Ask 요청은 사람이 지원되는 MCP App이나 정확한 연결 검토 화면을 조작할 때까지
대기합니다. Unit·Playwright는 `get_execution`, Integration은 `get_run`도 지원합니다.
조회나 텍스트 동의는 승인이 아닙니다. 두 사람용 인터페이스를 모두 사용할 수 없으면
제약을 보고하고 대기 상태를 유지하거나 취소합니다. 오래된 revision이나 검토 입력
변경에는 검토 갱신 또는 새 요청이 필요하며 다른 설정을 승인해서는 안 됩니다.
[인터페이스](interfaces.md)에 검사를 설명합니다.

## 설정과 준비 상태

관련 없는 필드를 보존하며 작성된 JSON을 직접 수정하고 같은 체크아웃으로
`configure validate`를 호출합니다. 중복·알 수 없는 키, 안전하지 않은 경로, 누락된
Compose 서비스와 의존성 변수 충돌이 흔한 오류입니다. 유효한 빈 설정은 애플리케이션
구성이 아닙니다. 설정 쓰기 API나 편집기는 없습니다.

비공개 값은 채팅에 올리지 않고 공유 설정 파일에서 안전하게 편집합니다. 값은 문자
그대로의 문자열이며 비밀 참조나 서버 환경 fallback은 없습니다. 새 요청은 새 값을
캡처하고 기존 요청은 수락한 입력을 유지합니다. 마스킹·캡처 한계는
[설정](configuration.md)에 설명합니다.

유효한 URL은 연결을 증명하지 않습니다. Docker·Compose, 이미지 빌드, health 진단,
내부 포트와 실제 소비하는 러너를 확인합니다. 컨테이너 내부 `localhost`는 그 컨테이너입니다.
관리 서비스 DNS와 `tests.env`가 앱에 맞아야 합니다. shared-local·remote에는 명시적인
접근 가능한 origin이 필요합니다. 각 실행은 새 임시 환경을 만들며 이전 환경을 재사용하지 않습니다.

## 수집, 제한과 정리

Integration은 `tests.directory`에서 정확한 요청 테스트와 도우미를 수집합니다.
최대 50개 파일, 파일당 200 KB, 전체 2 MB, 방문 항목 5000개이며 심볼릭 링크는 거부합니다.
확장자는 `.ts`, `.js`, `.json`과 루트 `pnpm-lock.yaml`입니다. 지원하지 않는 패키지·설정
입력은 번들을 거부할 수 있습니다. 테스트는 `.test.ts`, `.test.js`, `.spec.ts`, `.spec.js`로
끝납니다. 런타임·패키지 제약은 [테스트 작성](tests.md)에 설명합니다.

Unit Dockerfile은 의존성을 설치하고 `/workspace`를 복사하며 `/bin/sh`를 제공해야 합니다.
빌드·import 실패는 단언 실패가 아닙니다. 개별 테스트 timeout은 기본 2048 MiB·600초의
인스턴스 러너 제한과 별개입니다. 한도를 늘리기 전에 과도한 작업을 살피세요.
적용 범위와 종료는 [실행](execution.md)에 설명합니다.

정리는 테스트 판정과 별도로 읽습니다. `cancel_execution`과 지원되는 재시도를 사용한 뒤
실제 상태를 확인하세요. 일반 환경 정리는 이전 버전의 남은 자원을 제거할 수 있지만 새
수동 Container는 제공하지 않습니다. 정리 실패 시 근거와 소유 자원 식별을 보존하세요.
수정·미기록 초안을 강제 삭제해 정리 검사를 우회하면 안 됩니다.

문제 보고에는 버전·커밋, 인스턴스, 체크아웃, 실행 ID·종류와 처음 실패한 단계를 포함합니다.
로그·설정·산출물을 공유하기 전에 비공개 데이터를 검토하세요.
